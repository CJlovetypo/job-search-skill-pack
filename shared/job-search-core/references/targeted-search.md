# 岗位定向检索

用户表达岗位倾向但尚未选择方式时，必须先按 [搜索策略](search-strategy.md) 说明标题定向与全量 JD 综合判断的优劣并请用户选择。只有用户明确确认岗位标题相关定向搜索，才生成 `targeted` 计划；普通倾向、关键词或“快点”不能替代确认。已有明确选择直接沿用；agent 根据业务资料和用户目标生成计划，无须用户编写 JSON。

1. 沿用已明确的招聘方向、行业、城市和公司限制。
2. 阅读共享业务标签，推理候选公司，并保存每家业务依据和理由。业务未知时可以纳入待了解候选，不能将“没有标签”当作“确定不相关”。
3. 扩展职能相近词，保存每个词的语义理由。例：“房地产销售”可能对应“置业顾问”“房产销售”“新房销售”；“渠道销售”需要结合公司及 JD 检查。不要把此示例写成固定通用词典。
4. 将计划放进画像 `search_plan`，或用 `--search-plan 文件` 传给 `catalog` 和 `prepare`。随后沿用 collect、范围选择、全文评估、报告的原流程。

计划结构：

```json
{
  "mode": "targeted",
  "target": "用户明确的目标",
  "company_ids": ["真实来源库中的公司ID"],
  "company_reasons": [{"company_id": "真实来源库中的公司ID", "reason": "为何可能提供这种工作", "business_basis": "已读业务资料、URL或JD证据"}],
  "keywords": ["标题相近词"],
  "keyword_reasons": [{"keyword": "标题相近词", "reason": "为什么对应目标工作"}],
  "exclude_keywords": []
}
```

`search-plan-check --file 文件` 可检查计划。`catalog --profile 文件` 会展示候选、规模事实、城市排除与资料缺口；`prepare --profile 文件` 固定这次范围。三个 CLI 共用该行为。

执行优先级（逐来源强制执行）：

1. 用户已确认定向，且当前配置及方向存在 `verified_native_keyword` 证明、适配器支持：必须直接向数据 API 传入关键词，先搜索再返回；不先请求无关键词的全量列表。多词分别查询并按岗位 ID 去重，补齐命中岗位 JD。
2. 用户已确认定向，但支持情况未知、未验证、不支持或证明失效：不试猜关键词参数；无关键词完整获取约定范围的岗位列表并在本地搜索标题，补齐命中岗位 JD。不能只取首页或样本冒称全量；分页未完成、限流和失败须标记覆盖不完整。只能返回完整正文的适配器可以全量获取后本地筛选。
3. 用户选择全量：不进入本定向流程，按 `exhaustive` 获取完整 JD，结合标题、职责和要求判断相关性，不因标题未命中而提前排除。

原生关键词能力按完整配置和招聘方向分别保存于 `data/source-search-capabilities.json`。只有真实正例岗位 ID 仍返回、随机负例为空，且负例采集完成，才标 `verified_native_keyword`。有字段但未实测、当前接口为空、请求失败或筛选未生效均使用列表及本地标题筛选，来源继续启用。

常用 ATS 和 Workday 先筛标题再补正文；其他适配器先尝试列表，必要时仍会取得全量正文。运行覆盖记录实际策略和请求数，不保证每个来源都减少网络请求。多词结果去重，服务端可能搜索全文，因此最后还要核对标题。标题只决定候选，不能生成能力、意愿或投递评级。

已验证的原生关键词查询正常返回零结果时，不自动扩大公司或词表，也不擅自改为全量 JD 综合判断。API 能力未证实而全量获取列表后本地筛选，是上述必须执行的兜底，不属于扩大范围或改变搜索方式。报告明确候选公司、词表、排除词及“可能漏掉标题未体现的机会”。定向快照有独立计划指纹，不能作为全量缓存；定向结果不能更新全量城市标签。

维护能力证明：从仓库根目录运行 `node job-search/runtime/campus/scripts/audit-search-capabilities.mjs --per-provider=10`，默认每个平台每个方向抽测 10 个配置，其余逐项列为未证明原生检索并使用本地筛选。该参数控制抽测数量，不把抽测推广为全库验证。

验证当前库中全部尚未通过的参数候选，使用 `--pending`；先加 `--dry-run` 查看规模。`--concurrency=4` 控制并发（1–16），`--out=路径` 指定本次私有证据目录，重用同一批次目录可续跑。默认目录按 UTC 日期生成；需要重新联网实测时使用新目录。`--providers=51job_xyz` 可限定平台；`--no-publish` 只保存证据。`--replay-only --out=原目录` 对已有证据按当前规则离线复算并合入当时的正式档案，不重新请求接口，也不将旧采集时间更新为现在；不能与 `--pending` 同用。普通续跑也会复算缓存，缺失证据不得直接复用旧“通过”结论。不要并发运行多个会写正式档案的批次。已验证且配置及方向相同的记录在 pending 模式保留，无原生参数适配的来源仍列为本地标题筛选，不能据此认定接口本身不支持搜索。

新验证还检查三轮查询的实际列表请求：关键词确实发送、HTTP 成功、除关键词及分页外路由与筛选条件一致（包含决定门户的稳定请求头），避免方向发现变化导致误判。每项完成即保存私有证据，批次全部结束后原子更新正式能力档案。该证明仅覆盖接口检索能力，不等于证明某招聘方向有在招岗位，也不改变岗位方向判定规则。

现有关键词适配覆盖北森（`KeyWords`）、Moka/飞书（`keyword`）、Workday（`searchText`）、51job XYZ（`keyWord`）和海南华铁（`keywords`）。XYZ 在每页请求签名前写入关键词，仍需逐配置、逐方向通过实测后才用于定向检索。

进一步复核可加 `--deep`：刷新公开方向发现，将每项预算提高到 240 次请求、180 秒；正例最多取 5 页，必要时使用基准岗位标题中原有的完整词短语重试。备选词与实际请求留档，缓存复算只接受从原始标题可重建的词。

查询完整性与招聘范围分开核验：Workday 地点子范围的负例必须逐组请求成功、分页完整且服务端总数为 0；Moka/飞书缺少目标方向入口时，必须现有路由的全部上下文完整且每页总数及岗位均为 0。它们仍需通过正例 ID、实际参数、相同路由对照。通过只证明已请求路由的关键词能力，方向限制保存在 proof.scope_limitation，原采集 coverage.partial 不变，不代表社招入口或全国覆盖已经补全。

`--scope-file=文件` 可将复测限制在明确清单（JSON 数组，元素为 `key|mode` 字符串或 `{key,mode}`）；修复后的配置必须使用新 key 重新验证，旧配置证明不能沿用。已有 `identity_verification.identity_verified=false` 的明确主体核实失败会阻止采集并使旧岗位缓存失效；缺少主体证据字段不自动禁用来源。

同一对照批次在内存中复用一次公开方向发现结果，保证基准、正例与负例使用同一门户集合；下一次独立复核仍重新发现。此临时复用不改变日常采集的发现缓存，也不清除发现失败记录。深度模式单请求超时为20秒，仍受总时限和请求预算约束。

## 新增与修复来源的固定验收流程

基础获取能力验证通过后，所有新增、迁移、修复的 API 配置都必须额外核验关键词定向能力，按当前配置指纹和 campus/internship/social 分别记录，不能用同平台抽测替代。完整 JD、正常空列表及仅列表准入仍沿用原标准；定向能力未证实不阻塞基本取数可用性。

1. 先确认主体、招聘方向、地域范围、岗位 ID、分页与已取得的基础能力，再检查官网公开请求／前端契约是否公开关键词参数。禁止猜测参数后仅凭 HTTP 200 宣称支持；没有适配器也不能判为不支持。
2. 已有关键词适配器执行无词基准、真实标题正例、随机负例三组实际 API 请求，按本文的 ID、请求参数、路由一致性及负例完整性规则判断。配置或方向发生变化后不继承旧证明。
3. 每项输出 `supported`（已证实支持）、`unsupported`（有官方明确契约依据的不支持）或 `unconfirmed`（尚未证实），保留原因、时间、配置键及证据。无岗位、超时、限流、访问受限、无已确认适配器或对照未通过均为 unconfirmed，不能据此断言 API 不支持。遵守既有请求预算和访问限制。
4. 维护收尾必须检查所有受影响项已经完成判定和记录；尚有未处理项时不得称维护完成。记录为 unconfirmed 可以结束本轮有界验证，但报告必须列出原因和后续办法，不能称定向能力已通过。

`commitSourceRepair`（包括追加频道）以及两个正式 Waiqi 扩源应用入口会在注册表发布前保存私有待验证清单，位置为共享 `state/source-keyword-reviews/`。因此中断后可以续跑；未成功发布或已被后续配置取代的键不会误计为当前待办。只生成候选或预览不触发验证。运行时自动修复只登记待办并继续基本采集，主动维护收尾必须执行以下命令，不把日常求职变成全库维护。

```sh
# 只读查看全部待办，不受每平台默认抽样数量限制
node shared/job-search-core/scripts/audit-search-capabilities.mjs --maintenance --dry-run
# 执行所有当前待办；有界实测默认使用 deep 预算，断点证据保存在指定目录
node shared/job-search-core/scripts/audit-search-capabilities.mjs --maintenance --out=shared/job-search-core/state/maintenance/keyword-maintenance-本批次
# 收尾检查：仍有未处理项返回退出码 2；全部已有判定返回 0
node shared/job-search-core/scripts/audit-search-capabilities.mjs --maintenance --check
```

维护模式不接受 `--per-provider`、`--providers`、`--scope-file`、`--pending` 或 `--replay-only`，防止漏掉受影响项。`--no-publish` 仅保存私有结果，不能清除待办。`maintenance-results.json` 是逐项交付清单；`data/source-search-capabilities.json` 保留运行时判定，日常运行不依赖私有待办。旧 campus 路径审计命令兼容保留，实现统一归属共享层。发布使用互斥锁，并再次核对注册表和能力文件是否变化，发生并发变化时保留证据、重新运行，不覆盖新配置的结果。

其他经授权的维护入口必须复用待办登记函数；已有合法批量改动若尚未接入，可在同一维护命令附 `--register-before=修改前来源快照.json`，按前后差异补登记，不能直接编辑能力结论。每批使用独立输出目录；续跑只复算该配置的原始对照证据，不信任缓存的成功标签。

确有官方契约明确不提供关键词过滤时，可附 `--unsupported-review=复核清单.json`。清单为数组，每项包含当前待办的 `key`、`mode`、`finding: "official_contract_explicitly_disallows_keyword"`、`evidence_url`、本地原件 `evidence_file`、`reviewed_at` 和 `reason`。Agent 必须实际阅读原件确认限制；脚本只检查记录结构和证据存在，不替代语义核实。仅未找到搜索参数不满足此结论。公开记录不写本地原件绝对路径。
