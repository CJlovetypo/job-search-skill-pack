# 招聘链接修复

共用已知条件继承、主体歧义、材料缺失和只读范围遵循 [业务决策规则](../shared/job-search-core/references/decision-policy.md)。此入口独立于个人匹配，不索要简历；历史调查与正式配置修复分别交付。

目标是找回**同一招聘主体、同一招聘方向**的可验证入口，保留旧链接、推导依据、当次验证结果与回滚信息。工作在 job-search-skill-pack 仓库中；以下命令以仓库根目录为当前目录。依赖 Node.js 22+；实时取证使用宿主可用的网络或浏览器工具。

## 先查历史，再做最小范围验证

1. 从用户和现有采集失败记录确定公司、失效 URL、校招／实习／社招、目标地区及需要恢复的能力（入口、列表或完整 JD）。已有条件直接沿用。只有失效 URL 时，先从历史查主体；不能从租户拼写猜定雇主。
2. 读 [数据集说明](references/history-dataset.md)，按公司、失效域名分别查。记录中的 `evidence.file` 相对于数据集根目录，`location` 指向具体行或 JSON Pointer。

   ```sh
   node recruitment-link-repair/scripts/history.mjs --query=公司名 --family=wps --limit=50
   node recruitment-link-repair/scripts/history.mjs --host=失效链接的完整域名 --limit=50
   node recruitment-link-repair/scripts/history.mjs --kind=contracts --query=公司名 --limit=50
   ```

   `total` 大于 `returned` 时结果有截断，进一步按域名、平台、来源筛选或增大 `--limit`。Waiqi 接口记录可能只有公司 ID，用 `--kind=contracts --query=Waiqi公司ID` 追查。完整原始数据留在 `collections/`，无招聘链接的 4,165 家公司目录也保留在快照中。
3. 若本机没有历史数据，明确说明；可读当前 `shared/job-search-core/assets/sources.json`、Waiqi 候选和接口目录继续调查，但不能宣称检索过本地历史。Git 克隆不含原始数据，禁止因缺文件而重新批量抓取全库。
4. 根据 [修复方法与实际案例](references/repair-methods.md) 判断故障，选 1–3 个有证据的候选。跨届名称相同只用于候选检索，不自动合并主体。历史 `observed_at` 是抓取时间，`period_hint` 是表格届别；归档日不是当时接口验证日。
5. 在当前官方入口、实际跳转、公开配置或前端脚本中核实新地址。优先复用本仓库采集器；历史请求只作契约参考，匿名初始化会话，不重放归档 cookies、Authorization 或过期签名。需要浏览器时使用宿主支持的浏览器能力；遵守当地已安装的网络访问约定。

## 判断是否真正修好

分别报告这些维度，不能用一个“成功”抹平差异：

- **主体**：官方招聘入口与接口返回的组织／雇主是否一致，子公司过滤是否真的传到请求中。
- **方向和范围**：招聘类型、批次、国家／城市是否保留；页数、唯一岗位 ID 与总量是否收敛。
- **能力**：仅入口、仅列表、官方 API 正常空列表、完整 JD 各自成立到什么程度。完整 JD 需稳定 ID、职责、要求和官方详情 URL。
- **在招状态**：旧详情仍可读取不代表当前仍接受申请；在当前列表中未见也不能在分页未完成时断言下架。

429 按 Retry-After 冷却；登录／验证码／403 停止该轮参数试探；超时与 DNS 错误标记网络问题。项目结束、岗位下架、正常空列表不通过改年份或更换公司“修复”。同名异主体或渠道不确定时保留冲突并说明缺少哪项证据。

默认先验证最多 3 个候选，每个只取足够核对主体、列表和 JD 的样本；预算耗尽标记 `partial` 或待复核。样本通过后，才按用户原来的查询范围补齐分页。详见 [现有自动修复范围](../shared/job-search-core/references/source-repair.md)。

## 应用与交付

用户要求修复正式来源时，已验证的同主体、同方向修改可在授权范围内应用；若只要求分析或给候选，返回证据即可。`repair-source` 会修改注册表，运行前读上面的自动修复说明。它目前自动处理 Moka／飞书的有限变化，北森仅发现候选，不承诺跨平台迁移。

其他变更先保存新旧配置差异，再使用现有注册表加锁、比较旧值、原子写入的机制（`shared/job-search-core/scripts/lib/source-repair.mjs`）；不要覆盖其他任务已改的配置。跨平台变更需完成主体与适配器验证，不能直接调用原平台修复路径蒙混过关。新配置重新验证招聘方向和搜索能力；旧证明不自动继承。历史快照不改写，新证据使用新目录。

交付一份简短记录：旧 URL → 新 URL（或无可确认替代）、原因、历史证据路径、当次核验时间、主体／范围／能力／在招结论、是否已应用、备份或回滚位置、尚未解决的项目。查询脚本本身只读离线数据，不探测网络、不自动改注册表。

修复验收必须增加 [新增与修复 API 定向能力验证](../shared/job-search-core/references/targeted-search.md#新增与修复来源的固定验收流程)：基本取数恢复后逐配置、逐招聘方向完成关键词验证和记录，运行维护收尾检查；仅登记待办不能称全部完成。报告列出每项支持／不支持／未证实及原因。旧证明失效，未证实不阻塞基本取数。

提交函数要求明确写入策略：日常同范围参数修复使用 `access: safe_existing`，主动维护使用 `access: maintenance`。完整证据与回滚记录写共享私有 state，公开来源仅留摘要；调用方不能用 force 绕过白名单。
